Scope: Training Experience V1 for Tome: Martial Arts (Flutter) — replaces the placeholder timing-bar with a real interactive target-strike exercise. New surface inside the established "Lineage Hall" world (seed 6f69b7e6), not a replacement of it. Visitor mode: Operate (the player performs a short skill task), with strong scene presence. It is the deliberate counterpoint to auto-combat: combat is automatic / observational / build-validation; training is active / skill-based / player-controlled / repeatable.

Audience & job: a solo roguelike player at the Tome between fights who has selected one item or technique and pressed Train. They want a tight ~15-25s physical beat that ends in real progression and, sometimes, a surprise. The whole exercise must be understandable with zero instructions — target, hit it, another, hit it faster.

Action / task: clear 9 circular bullseye targets across 3 escalating waves (3 targets per wave, all live, tap in any order; the next wave spawns at fresh coordinates once the current one resolves). Tap/click only — one gesture, mouse and touch identical. Hit quality is tap distance from the ring centre (perfect / good / weak / miss). Difficulty ramps: per-target lifetime ~1400ms in wave 1 tightening to ~800ms by wave 3; wave 3 coordinates more spread. A timed-out or outside tap still resolves the target (and still produces an engine attempt).

Proof / content: every target resolves to one real `TrainingAttempt` carrying true spatial data (`actionX/Y`, `targetX/Y`, `tolerance` in a normalized 0..1 field space) and true temporal data (`signalTimestamp`, `responseTimestamp`, `maxAcceptable` in ms). A client-side `TargetStrikeExercise implements TrainingExercise` (in `lib/core/engine/`) runs the engine's own `PrecisionExercise` + `ReactionExercise` over that history and returns the union of their profiles — `accuracy / precision / control` from one, `reaction / speed / consistency` from the other, no key overlap. That merged `TrainingProfile` is the sole input to the engine's unchanged `trainingGain`, learning threshold, and `evolveTechnique` weighting. The result screen's HITS / PERFECT / MISSES / AVG REACTION / PRECISION% are display aggregates of the same captured data; the engine's returned gain and evolution are the source of truth.

Chosen direction: "The Lineage Hall" ink language, applied to a different room. Canvas only — `ink.dart` primitives (`handRect`, `inkStroke`, raking light `kRakingLight`), `HallTheme`, `InkButton`; no imported art. One exercise-logic core, two presentation skins bound at runtime by `CharacterAdapter.currentView().martialTradition`. WEST: a fighter silhouette + hanging bag in a restrained dark gym; targets sit at head / chest / ribs / gut strike zones; a hit shifts the silhouette and swings the bag on that zone. EAST: a wooden dummy / bamboo post; targets at upper / centre / lower zones on arms / torso / side branches; a hit judders the branch and rocks the post. Zones are chosen from a normalized layout drawn from the seeded `EngineSession.rng` (`RngService`) — never pixel coordinates, never a fixed three-slot arrangement; a `LayoutBuilder` transform maps 0..1 to the rendered field, aspect-guarded so no wave places a target off-frame. Layout: scene object owns the vertical mid-band and the frame's attention; a slim top rule (`TRAINING · <SUBJECT> · WAVE 2 / 3`); a deliberately de-emphasized bottom strip of `SPEED` / `PRECISION` hairline meters + `MISS` count, no raw ms mid-exercise. Feedback carries in shape and motion, never colour alone: perfect = crisp vermilion seal-stamp + fast inward ring-collapse + scene recoil; good = ring-collapse, lighter; weak = a soft dent; miss = a struck-through ring that fades + a small scene sway, never a punish. At most ~4 concurrent lightweight resolving animations (a `Ticker` value or `TweenAnimationBuilder` per resolving target — no controller pool), all collapsed to instant under reduced-motion.

Memorable moment: the surprise evolution reveal. The player never knew it was coming; for technique training a strong result may trip `evolveTechnique` engine-side. After the compact result summary, a held, slower beat — `NEW TECHNIQUE / <name> / EVOLVED FROM / <name> / [Continue to Tome]` — visually stronger than an ordinary mastery number. This is a signature game moment; the client only presents what the engine decided.

Constraints: engine owns mastery / learning / evolution / training rules / thresholds — the client owns target presentation, input, timing capture, visual feedback, screen flow, and nothing else. No second mastery or evolution system, no duplicated thresholds, no client deciding an evolution chain. Zero engine change (Precision + Reaction composed in the sanctioned `lib/core/engine/` boundary). `TrainingAdapter.trainItem/trainTechnique` gain an optional `TrainingExercise base` defaulting to `const TimingExercise()` so the three existing adapter tests stay green; the exercise screen passes `const TargetStrikeExercise()`. `TrainingBloc` stays app-level across the `trainingPreparation → training → trainingResult` go_router phases; `AttemptSubmitted(double)` becomes a richer per-target `TargetResolved` event, `_requiredAttempts` 3 → 9, `TrainingCompleted` / result flow unchanged. The `TrainingPresentation` seam contract holds: presentations report raw client data (normalized tap point + ms latency), never anything build_engine-shaped. PRODUCT.md game-a11y baseline: shape-not-colour, scalable text, full prefers-reduced-motion, `Semantics` on the drawn field. Anti-goals: no rhythm game, no combos / stamina / enemy AI / 3D / physics, no screen-filling effects, no hardcoded pixel target coordinates, no per-tap widget-tree thrash, no cartoon fighting-game UI, no caricature of either martial tradition. V1 implements `TargetStrikeExercise` only; the `TrainingExercise` abstraction is left open for future exercise screens, not built.

Unresolved / follow-up: (1) the Precision+Reaction merge is client-side — no shared engine `CompositeTrainingExercise` primitive (deliberate, revisit only if another surface needs to compose exercises). (2) All three targets in a wave light on wave-spawn, so a target's `reaction` score folds in time spent clearing its wave-mates — it rewards fast even clearing, not pure single-stimulus reflex. (3) `TrainingResultView.gain` is a single scalar applied to one axis; the consequence line shows the axis that actually moved (item mastery / technique learning / technique mastery), not a split. (4) V1 is tap/click only — no keyboard target traversal (needs a follow-up for full input a11y). (5) Exact per-wave lifetime curve and the perfect/good/weak radius fractions (centre ≤ ~0.3r, good ≤ ~0.65r, weak ≤ r, r ≈ 7-10% of the field's min dimension) are left to tune to feel within the ranges above. (6) Both canvas scenes are V1 placeholders behind the `TrainingPresentation` seam — a richer 2D/3D pass is a later task.
